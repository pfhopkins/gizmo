# omp_thread_invariance

Runs one problem with 1 and with N (up to 8) OpenMP threads from the same binary and compares
the final snapshots, once with MFM and once with MFV.

Every threaded loop in the MFM configuration (density, gradients, hydro, timesteps) works per
particle with a fixed neighbour order, so the thread count should not change a single bit; the
MFM variant requires bit-identical snapshots. MFV exchanges mass between cells with `omp atomic`
updates, whose order legitimately changes the last bits, so the MFV variant requires the total
mass to agree to 1e-12 instead: a lost update moves it by the exchanged mass.

## Why the build is unoptimized

`BUILD_UNOPTIMIZED` in `Config.sh` makes the Makefile append `-O0`. At `-O1` and above GCC keeps a
shared-but-racing loop counter in a register and writes only its final value back to memory, so
the race exists in the source but not in the binary. At `-O0` every access goes to the shared
location. The test asserts the flag appears in the run's compile-settings listing.

## Problem

A 3D periodic box with 16^3 cells (generated by `make_omp_thread_invariance_ics.py`):
- MHD with Dedner cleaning
- a central over-pressured sphere whose shock spreads the cells over several timebins and wakes
  up cells ahead of it
- a shear flow that switches on turbulent metal diffusion everywhere
- 14 passive metal species, so the per-species loops are long. Species s and s+7 start identical
  and get identical physics, so every run also requires each pair to stay bit-identical, which
  catches per-species indexing errors even with one thread.

The runs start with restart flag 2, because a flag-0 start resets IC metallicities to a uniform
value. The test asserts that metallicity changed in most cells, so metal exchange cannot silently
turn into a no-op.

Each variant takes about 15 s including the build.

## Known sensitivity

- MFM: fails when the species/component loop counter in `hydro_final_operations_and_cleanup` and
  `hydro_force_initial_operations_preloop` is shared across the `omp parallel for`. The 8-thread
  run aborts in `density()`, and the runs already diverge at 2 threads.
- MFV: fails when `out2particle_hydra` adds to `dMass` non-atomically while neighbours update it
  atomically. The total masses differ at ~1e-6 and change from run to run.
- MFV: fails when the advective metal flux in `hydro_evaluate.h` updates only one species (the
  leftover index `k` instead of a loop over species). Species 3 diverges from its twin even with
  one thread.

Not covered: when several active neighbours wake the same inactive cell in one hydro pass, the
cell's new timebin comes from whichever neighbour writes `P[j].wakeup` last (`hydro_evaluate.h`), so
it can depend on thread scheduling. No such difference appears here, even in a 1000x stronger blast.
