# omp_thread_invariance

Runs one problem with 1 and with N (up to 8) OpenMP threads from the same binary and compares
the final snapshots, once with MFM and once with MFV.

Every threaded loop in the MFM configuration (density, gradients, hydro, timesteps) works per
particle with a fixed neighbour order, so the thread count should not change a single bit; the
MFM variant requires bit-identical snapshots. MFV exchanges mass between cells, and the order in
which neighbours' contributions are summed legitimately changes the last bits, so the MFV variant
requires the total mass to agree to 1e-12 instead: a lost update moves it by the exchanged mass.

A third check, `test_omp_domain_decomposition`, runs the same problem on 2 MPI ranks with 1 and N (up to 4)
threads for a few steps and requires the first 5 domain decompositions (the `Balance:` and `Domain adaptive weights:`
lines) to agree. The first one happens at startup, before any physics, and with correct code they agree for about
10. Snapshots are not compared there: multi-rank runs are reproducible at a fixed thread count, but not bit-identical
across thread counts.

## Why the build is unoptimized

`BUILD_UNOPTIMIZED` in `Config.sh` makes the Makefile append `-O0`. At `-O1` and above GCC keeps a
shared-but-racing loop counter in a register and writes only its final value back to memory, so
the race exists in the source but not in the binary. At `-O0` every access goes to the shared
location. The test asserts the flag appears in the run's compile-settings listing.

## Problem

A 3D periodic box with 16^3 cells (generated by `make_omp_thread_invariance_ics.py`):
- MHD with Dedner cleaning
- a central over-pressured sphere whose shock spreads the cells over several timebins and wakes
  up cells ahead of it
- a shear flow that switches on turbulent metal diffusion everywhere
- 4 passive metal species (1 + the 3 STARFORGE feedback tracers), so every per-species loop runs.
  Species s and s+2 start identical and get identical physics, so every run also requires each
  pair to stay bit-identical, which catches per-species indexing errors even with one thread.

The runs start with restart flag 2, because a flag-0 start resets IC metallicities to a uniform
value. The test asserts that metallicity changed in most cells, so metal exchange cannot silently
turn into a no-op.

Each variant takes about 15 s plus the build.

## What it guards

The plain `omp parallel for` loops in `hydro/hydro_toplevel.cc` (`hydro_force_initial_operations_preloop`,
`hydro_final_operations_and_cleanup`), `mesh/neighbor_loop_runner.cc` and `domain/domain.cc` (`domain_sumCost`),
and the MFV per-species advective flux in `hydro/hydro_functions.h`. On starforge_dev, where these checks were
written, the same test:

- MFM: failed when the species/component loop counter in the two hydro_toplevel loops was shared across the
  `omp parallel for` (the 8-thread run aborted in `density()`, and the runs already diverged at 2 threads).
- MFV: failed when a cell's own `dMass` was added non-atomically while neighbours updated it atomically (total
  masses differed at ~1e-6 and changed from run to run). Here the pair kernel's results are written back after
  the kernel, so the same hazard does not exist in that form.
- MFV: failed when the advective metal flux updated only one species (a leftover index `k` instead of a loop
  over species): species 3 diverged from its twin even with one thread.
- Decomposition: failed when `domain_sumCost` shared the top-tree leaf index between threads. Particles were
  counted in the wrong leaves, and the startup decomposition went from exact balance (memory balance 1) to
  1.0007-1.005, even at 2 threads.

Not covered: when several active neighbours wake the same inactive cell in one hydro pass, the
cell's new timebin comes from whichever neighbour writes `P[j].wakeup` last, so it can depend on
thread scheduling. No such difference appeared on starforge_dev, even in a 1000x stronger blast.
