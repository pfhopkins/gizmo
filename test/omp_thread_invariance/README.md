# omp_thread_invariance

Runs one problem with 1 and with N (up to 8) OpenMP threads from the same binary and requires
bit-identical final snapshots.

Every threaded loop in this configuration (density, gradients, hydro, timesteps) works per
particle with a fixed neighbour order, so the thread count should not change a single bit. A
data race does: a shared loop counter, a non-atomic update of shared data, or a result that
depends on which thread wrote last.

## Why the build is unoptimized

`BUILD_UNOPTIMIZED` in `Config.sh` makes the Makefile append `-O0`. At `-O1` and above GCC keeps a
shared-but-racing loop counter in a register and writes only its final value back to memory, so
the race exists in the source but not in the binary. At `-O0` every access goes to the shared
location. The test asserts the flag appears in the run's compile-settings listing.

## Problem

A 3D periodic box with 16^3 cells (generated by `make_omp_thread_invariance_ics.py`):
- MHD (MFM, Dedner cleaning)
- a central over-pressured sphere whose shock spreads the cells over several timebins and wakes
  up cells ahead of it
- a shear flow that switches on turbulent metal diffusion everywhere
- 14 passive metal species, so the per-species loops are long

It takes about 10 s including the build.

## Known sensitivity

Fails, with the 8-thread run aborting in `density()` and already diverging at 2 threads, when
the species/component loop counter in `hydro_final_operations_and_cleanup` and
`hydro_force_initial_operations_preloop` is shared across the `omp parallel for`.

Not covered:
- Races whose only effect is to reorder floating-point sums, such as `omp atomic` accumulation
  (MFV's `dMass`). Those break bit-identity legitimately, so such configurations do not belong in
  this test.
- The WAKEUP last-writer race, which has no observable effect here.
