# How to add a new test problem

## What belongs in `test/`

The test problems shipped with GIZMO are a curated set. Each one meets at least one of these criteria, and most meet all three:

1. it validates physics or numerics that no other test covers;
2. it has pedagogical value: it shows users how a module behaves and how to set up a problem with it;
3. it sets up a real physics problem that users can build on.

Checks written to confirm that a bug is fixed, or that a pull request does what it says, are valuable, but they belong with the pull request (describe them and what they showed in its description), not in `test/`. If you think a new problem meets the criteria above, propose it explicitly in your pull request; adding a test problem needs the branch maintainer's approval. See the "Contributing Changes Back" section of the user guide (`scripts/gizmo_documentation.md`).

## Anatomy of a test

A test named `my_test` lives in `test/my_test/` and has:

1. `Config.sh`: the compile-time flags GIZMO is built with for this test. Include `STOP_WHEN_BELOW_MINTIMESTEP` so a run that stalls stops with a diagnostic instead of running on.
2. `my_test.params`: the runtime parameters. Keep the run short (minutes on a laptop at the default rank count), with `OutputDir output`.
3. `test_my_test.py`: the pytest module (pytest collects files named `test_*.py`).
4. `README.md`: what the problem is, what it checks, and where the reference solution comes from.
5. Initial conditions, `my_test_ics.hdf5`, either:
   - generated by a script `make_my_test_ics.py` that the test module imports and calls (preferred for anything cheap to build: the test is then self-contained and the IC can be regenerated at any resolution), or
   - downloaded on the fly by `download_test_files` from `http://www.tapir.caltech.edu/~phopkins/sims/` (with a mirror at `https://users.flatironinstitute.org/~mgrudic/gizmo_tests/my_test/`), for ICs too expensive to rebuild. Large files are never committed to the repository.
6. Optionally a reference solution, `my_test_exact.txt` or `my_test_exact.hdf5`, generated or downloaded the same way.

## Writing the test module

The `gizmo.test` module (source in `python_src/gizmo/test.py`) does the building, running and bookkeeping. Test modules are run from the repository root (that is where `pytest` is started), and the helpers take and return paths relative to it. The main entry points:

| Function | Purpose |
|---|---|
| `build_and_run_test(name, ranks, threads, extra_config_flags=(), param_overrides=None, timeout=None)` | Build with `test/name/Config.sh` (plus any extra flags), fetch missing ICs, run, and check that the run exited cleanly and reached `TimeMax`. Variants with extra flags write to their own output directory. |
| `default_mpi_ranks()`, `default_omp_threads()` | The standard rank and thread counts. Two ranks is the minimum that exercises the exchange between ranks; always test with at least two. |
| `get_final_snapshot(name, extra_config_flags=())` | Path of the last snapshot of a run (variant-aware); refuses a run that was killed or stopped short. |
| `assert_final_time(snapshot, name)` | Assert the snapshot is at `TimeMax`. |
| `assert_snapshots_are_close(snap1, snap2, fields, rtol, atol)` | Compare gas fields of two snapshots. |
| `get_cooling_tables(test_dir)` | Fetch `TREECOOL` and the cooling tables, for tests with `COOLING`. |
| `parse_params(params_file)` | Read a parameterfile into a dict. |
| `run_test(name, ranks, threads, restart_flag=0, param_overrides=None)` | Run an already-built binary, e.g. with a restart flag; use it rather than writing `mpirun` by hand. |
| `mpi_launch_command(ranks, threads)` | The launcher prefix (everything before `./GIZMO`), for the rare test that must start GIZMO itself. |

A minimal test module:

```python
"""my_test: <one line on what it checks>"""
from pathlib import Path
import h5py
import pytest
from gizmo.test import (build_and_run_test, get_final_snapshot, assert_final_time,
                        default_mpi_ranks, default_omp_threads)

TEST_NAME = "my_test"
TEST_DIR = Path(__file__).parent


def generate_ics():
    ic_file = TEST_DIR / f"{TEST_NAME}_ics.hdf5"
    if not ic_file.exists():
        from make_my_test_ics import make_my_test_ics
        make_my_test_ics(str(ic_file))


@pytest.mark.parametrize("num_mpi_ranks", (default_mpi_ranks(),))
@pytest.mark.parametrize("num_omp_threads", (default_omp_threads(),))
@pytest.mark.parametrize("extra_config_flags", [(), ("SOME_VARIANT_FLAG",)], ids=["baseline", "variant"])
def test_my_test(num_mpi_ranks, num_omp_threads, extra_config_flags):
    generate_ics()
    build_and_run_test(TEST_NAME, num_mpi_ranks, num_omp_threads, extra_config_flags)
    snap = get_final_snapshot(TEST_NAME, extra_config_flags)
    assert_final_time(snap, TEST_NAME)
    # the pass/fail criterion: here total gas mass, for a problem with no sources or sinks of gas;
    # replace it with the problem's own physical criterion (e.g. an analytic or converged solution)
    mass_initial = total_gas_mass(TEST_DIR / f"{TEST_NAME}_ics.hdf5")
    mass_final = total_gas_mass(snap)
    # 1e-6 suits single-precision output; tighten it when the output precision and method justify it
    assert abs(mass_final / mass_initial - 1) < 1e-6, f"gas mass changed by {mass_final / mass_initial - 1:.3g}"


def total_gas_mass(filename):
    """Total gas mass in a snapshot or IC file: from the Masses dataset, or from the header's
    MassTable when every gas element has the same mass and no Masses dataset is written."""
    with h5py.File(filename, "r") as f:
        if "PartType0/Masses" in f:
            return f["PartType0/Masses"][:].astype(float).sum()
        header = f["Header"].attrs
        return float(header["MassTable"][0]) * float(header["NumPart_ThisFile"][0])
```

Diagnostic plots are encouraged (save them in the test directory, without overwriting another variant's), but pass/fail must come from explicit assertions. Generated plots and run outputs are not committed unless explicitly approved as reference material.

## Choosing the pass/fail criterion

The test should check a physical statement with a stated tolerance: agreement with an analytic or converged solution, a conservation law, a convergence rate, an equilibrium that must hold. Comparing against a stored snapshot from an earlier run of the code only shows that nothing changed, not that the answer is right, and it fails on any legitimate improvement; use it only when there is genuinely nothing better, and say so in the README. Set the tolerance from what the method should achieve at the test's resolution, and check that the test fails when the physics it targets is broken (for example by disabling the module). Never loosen a tolerance just to make a run pass.

## Useful environment variables

| Variable | Effect |
|---|---|
| `GIZMO_TEST_SKIP_BUILD_RUN=1` | Skip building and running; evaluate snapshots already in `test/<name>/output*` (e.g. from a run on another machine). |
| `GIZMO_TEST_TIMEOUT=<seconds>` | Kill (and skip) any GIZMO run longer than this. See `how_to_run_tests.md` for the outer pytest timeout. |
| `GIZMO_TEST_MPI_LAUNCHER` | Launcher for systems that do not use `mpirun` or `srun`, e.g. `"ibrun -n {ranks}"`; `{ranks}` and `{threads}` are substituted. Inside a SLURM allocation the tests already use `srun`. |
| `GIZMO_EXTRA_CONFIG_FLAGS` | Flags appended to every build without entering the variant identity, for sweep-wide A/B comparisons. |

## Compile-only coverage

`test/compile_suite/` builds GIZMO (without running it) under many `Config.sh` flag combinations. If your feature adds flags, or combinations that other modules must compile with, add rows to `COMPILE_CONFIGS` in `test/compile_suite/test_compile_suite.py`, and run it with `pytest test/compile_suite`.

## Document the test

Add the problem to the "Test Problems" section of the user guide (`scripts/gizmo_documentation.md`): what it is, what it checks, and how to run it.
